# V0.6 Notebook Workbench Architecture

## Goal

Make SparkLab practice happen inside a notebook environment that feels operationally familiar to Microsoft Fabric users while keeping the implementation honest about what is real and what is simulated.

## Surface hierarchy

```text
App header
└─ Ribbon / command bar
   ├─ Run controls
   ├─ Virtual session profile
   ├─ Notebook runtime
   └─ Attached lakehouse

Workbench
├─ Global rail
├─ Explorer
│  ├─ Data items
│  │  ├─ DuckLake item
│  │  ├─ Tables / fields
│  │  └─ Files
│  └─ Resources
│     ├─ Mission
│     ├─ Truth pack
│     └─ Reference contract
├─ Notebook canvas
│  ├─ Markdown mission cell
│  ├─ Editable code cell
│  └─ Result / Spark summary
└─ Diagnostics
   ├─ Spark UI
   ├─ Lakehouse
   ├─ Quality
   ├─ Cost
   └─ Hints
```

## Runtime truth model

### PySpark Training

```text
PySpark-style source
→ safe parser / SparkLab plan
├─ semantic execution path → DuckDB / Polars / MotherDuck
└─ physical model → stages / tasks / shuffle / AQE / cost
```

### SQL (DuckDB)

Real SQL path against the attached DuckLake/local data model.

### Polars

Real lazy DataFrame path for selected notebook missions.

### MotherDuck SQL

Cloud SQL path when credentials/connectivity are present.

## Design-system policy

The current implementation uses Fluent 2-compatible tokens/patterns without a hard package dependency. This keeps the standalone build offline-capable. A future React pass can replace local primitives with Fluent UI 2 components without changing the information architecture.
