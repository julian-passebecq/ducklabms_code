# V0.8 Release Report — Truth, Calibration and Clean-Root Reliability

## Scope

V0.8 is a debugging and correctness pass over V0.7. It does not redesign the Fabric-inspired shell. It concentrates on whether the workbench says something is real only when the implementation can support that claim.

## Defects found and fixed

### Root test command failed after clean unzip

**Before:** `pytest -q` failed during collection with `ModuleNotFoundError: services` unless `PYTHONPATH` was manually configured.

**Fix:** added Python package markers and a root `pytest.ini` with `pythonpath = .`.

**Gate:** root `pytest -q` now passes.

### UI could imply result rows were executed

**Before:** calibrated Spark simulation could display sample rows in a way that was easy to read as the result of a 184M-row query.

**Fix:** result evidence is explicitly split into compiled semantics / calibrated distributed simulation / real full-data row execution. Full-data execution is currently withheld; samples are reference truth only.

### Standalone Run could complete a mission without verification

**Before:** dependency-free fallback marked a mission complete on Run and displayed `SUCCEEDED` even though no parser/grader/backend was involved.

**Fix:** standalone now attempts the local FastAPI notebook endpoint for PySpark. Offline mode is a reference preview. Mission completion requires `grade.pass`; Lakehouse snapshot/consumer verification likewise require verified completion.

### Retail join and skew were conflated

**Before:** a combined Retail exercise mixed a small broadcast dimension and a hot aggregation key into a single training objective.

**Fix:** calibrated truth packs are now separate:

- `retail_broadcast_join_03`
- `retail_customer_skew_04`

Each has independent grading and simulation intent.

### Generated partition evidence contradicted configured skew

**Before:** generated synthetic partition sizes did not necessarily preserve the truth pack's median/largest values.

**Fix:** `normalized_partitions` builds a deterministic vector that preserves total bytes, requested median and requested maximum before AQE splitting.

### Stage evidence was too coarse

**Fix:** every modeled stage now reports P50/P95/max task duration, max partition size and skewed task count in addition to workers/tasks/duration/spill.

### Notebook Stop was decorative

**Fix:** React workbench Run uses `AbortController`; Stop aborts the current HTTP request. Standalone provides the same local-request cancellation behavior.

### React Plan rendering could crash

**Before:** `training_plan` could be rendered as a raw object.

**Fix:** formatted JSON rendering.

## Calibrated Retail baseline

Known case facts:

```text
orders                 184,229,821 rows / 26.4 GB / 286 Parquet files
customer segment dim        43,281 rows / 6.4 MB
shuffle partitions             200
median partition              91 MB
largest partition           1,656 MB
hot key               CORPORATE_ACCOUNT_01
```

Mission 03 deliberately withholds catalog size statistics from the modeled optimizer so the starter join has a physically inefficient but semantically correct baseline. Explicit broadcast changes only the join strategy; the customer aggregation still shuffles.

Mission 04 starts directly from the customer aggregation problem so the learner sees that adding workers or repartitioning on the same key does not remove data skew. AQE may split the known large partition.

## Truth levels

### Deterministic / verified by implementation

- whitelisted PySpark AST parsing
- generated relational plan/SQL for supported API
- exercise truth-pack facts
- grading rules
- virtual partition vector construction
- scheduler arithmetic/cost arithmetic

### Dataset-grounded model

- exchange boundaries
- virtual tasks/executors
- task duration model
- shuffle movement
- AQE split behavior
- spill risk
- wall-clock range/point estimate
- Fabric-like / Databricks-like usage equivalents

### Not claimed in V0.8

- full 184M-row result execution from the notebook UI
- real network shuffle
- JVM executor/GC behavior
- exact Fabric or Databricks proprietary scheduler behavior
- vendor invoice amounts
